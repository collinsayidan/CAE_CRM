# CAE CRM business upgrades

This release implements the first usable version of all twelve agreed workstreams. Existing workspace records, legacy member access, simple workflows, billing and the daily maintenance job are retained. It adds no runtime dependency.

| Workstream | Delivered | Boundaries and rollout checks |
| --- | --- | --- |
| 1. Pipelines | Workspace-owned processes; stage labels, probability and contact/value/source gates; editable stages; existing open-deal transfer; UI/API support; custom stages in charts, filters and assistant tools. | Existing deals remain in Default sales until explicitly transferred. Custom stage edits preserve deal IDs. Review saved filters and stage-based workflow conditions after renaming a stage. Won/Lost remain system outcomes. |
| 2. Permissions | Admin, member, manager, sales, support and finance; own, department or workspace visibility. Shared database boundary scopes record reads/writes, associations, attachments and timelines. | Only admins change access, export or delete. Existing member access stays unchanged. API keys remain explicitly admin-issued workspace credentials, independent of a staff session's record scope. Departments are maintained on profiles. |
| 3. Mailbox | Contact-specific full plain-text conversations fetched on demand from the current person's Gmail/Outlook; sending through that mailbox; single-use send requests; continuation-aware mailbox logging. | Bodies/attachments are not imported or retained. Sending is disabled until the host opts in and the user grants the extra OAuth scope. No automatic resend after an uncertain send. Plain-text rendering excludes remote HTML/tracking pixels. Recent conversation fetch is limited to 30 messages. |
| 4. Calendar | Current person's connected calendar view; public 30-minute booking links; external event creation; local reservations and meetings; collision checks, UTC storage and UK display. | External events are read on demand, not bulk imported into shared tasks. Existing task edits do not automatically modify provider events. Without calendar permission, the page explicitly checks CRM bookings only. Weekday booking hours are initially fixed at 09:00–17:00. External calendar failures are visible; a locally reserved slot is not lost. |
| 5. Workflows | Six-step chains, relative delays, conditions with skip/continue branches, task/notification/assignment/lifecycle actions, execution history, pause/resume and failed-step retry. | Complements existing one-action rules. Each step is transactional after a worker claim. Conditions are equality checks on owner, deal stage, ticket priority or source. Templates are snapshotted into queued runs. |
| 6. Sequences | Up to six email/task steps, contact enrollment, execution state, stop control, duplicate-enrollment prevention, consent/delivery checks and signed unsubscribe links. | Email sequences require marketing opt-in and a connected business reply-to mailbox. Observed replies, bookings, won deals and opt-outs stop follow-up. Mail sync runs before outbound follow-ups. Failures and uncertain deliveries need review, rather than automatic resend. Definition snapshots protect existing enrollments. |
| 7. Reporting | Allowlisted deals/tickets/invoices builder; grouping; date ranges; equal-length prior-period comparison; saved definitions; weekly emails to the creating admin. | Reporting uses creation date (invoice issue date). Weekly delivery covers the latest seven days. Schedules disable when the creator/recipient is no longer an admin. Does not claim arbitrary joins, attribution or a full BI designer. |
| 8. Forecasting | Monthly expected-close view; Pipeline/Best case/Commit/Omitted categories; weighted forecast; manager/admin reviews; review history; individual monthly targets. | Categories show separate totals, not cumulative buckets. Targets are stored separately from existing workspace targets. Close-date changes remain on existing record timelines. No predictive AI claim. |
| 9. Customisation | Ordered custom fields, conditional applicability, required fields on team edits/API saves, four arithmetic calculated-number operations and industry templates. | Required settings don't block public lead capture. Conditional inputs remain accessible without JavaScript; their applicability is explained, and irrelevant values are hidden in the record summary. Layout ordering covers custom fields, not arbitrary rearrangement of every built-in panel. |
| 10. Portal | Explicit customer membership; email proof; 15-minute single-use sign-in links; eight-hour sessions; immediate revocation; own quotes/tickets or explicit company-wide access; invoice payment and quote acceptance links. | Draft quotes and internal notes/timelines are excluded. Company access includes all company invoices, project status, quotes and tickets: administrators must choose it deliberately. Invoice PDFs/payments and quote decisions reuse existing protected public flows. Portal tickets are initially read-only. |
| 11. Onboarding | Persistent setup guide and status checks; consultancy, agency and IT-support templates; direct links to setup areas. | Applying a template is explicit, once per workspace; adds fields/processes without replacing records. Templates aren't required. |
| 12. Reliability/mobile | Responsive layouts; keyboard/forms instead of drag-only actions; database readiness; worker heartbeat; overdue/failure/sync visibility; request timings; queue indexes; read-only restored-backup verifier. | Production backup restoration, live provider consent, mobile visual review, load testing and host alert delivery must be verified on the deployment. The health screen does not certify a restore or uptime guarantee. |

## Activation on Coolify

1. Review and merge the PR, then confirm the deployment and `/readyz`. Schema changes are additive and applied on startup. Take a database backup first; do not reverse the database schema to roll back application code.
2. Keep `python cron.py` running **once daily** (existing invoice reminders and maintenance). Do not increase its frequency.
3. Add a separate scheduled task `python worker.py` at `*/5 * * * *`. It requires `CRON_SECRET` and `CAE_BASE_URL=https://cae.collinalitics.co.uk`. It checks a bounded mailbox batch, then queued workflows, follow-ups, scheduled reports and webhook retries. Existing provider cursors advance only after pagination finishes. A database lease prevents overlapping workers. Review System health for a stale heartbeat or delivery errors.
4. To enable connected sending, set `CAE_MAIL_SEND_ENABLED=1`; add Google's `gmail.send` or Microsoft's delegated `Mail.Send` to the registered OAuth app. Google's existing read scope is restricted and may require verification/security assessment. Reconnect each mailbox to grant permissions; old tokens are not assumed to have them.
5. To enable calendar features, set `CAE_CALENDAR_ENABLED=1`; enable Google Calendar API and allow `https://www.googleapis.com/auth/calendar.events`, or Microsoft delegated `Calendars.ReadWrite`. Reconnect, then test with a dedicated calendar. If a provider omits the scope in its token response, the additional feature stays disabled until a verified grant is recorded.
6. Configure the business reply-to mailbox, connect it, and resolve sync errors before enrolling anyone in an email sequence. Configure Resend and sender domain for sequence/portal/report messages. No customer is automatically enrolled and no portal membership is automatically granted.
7. Review each role and record scope with a non-admin test account. Check contacts, search, attachments, records linked across teams and finance access. Check portal membership with two different customer accounts and one revoked account.
8. Restore a backup into a **separate** throwaway database using the host's tools. With writes paused or a matching source snapshot, set `RESTORED_DATABASE_URL` and run `python verify_restore.py`. It compares ordered table contents and row counts, checks SQLite integrity/FKs when applicable, and refuses identical source/target database identities. It never restores, drops or modifies a database. Compare like-for-like backup snapshots: ongoing production writes will cause expected mismatches.
9. Review errors with existing Sentry monitoring (`SENTRY_DSN`). The app logs slow endpoint names, not customer URLs or tokens. Add external uptime/readiness alerts in the host's monitoring system.

## Validation

`python -m pytest -q` runs the existing regression suite and `tests/test_business_roadmap.py`. GitHub repeats tests on SQLite/PostgreSQL and builds/starts the Docker image. The SQLite restore fixture is intentionally skipped on PostgreSQL; production restore verification needs a separately restored target.

Browser/mobile visual acceptance, real OAuth consent, real calendar invitations, scheduled host tasks, production load and production backup restoration are separate rollout checks, not implied by unit tests.
